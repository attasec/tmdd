# TMDD Schema and Lint Reference

Exact file formats accepted by `tmdd lint` (v0.5.x), the review traversal that consumes
them, and every validation rule. Read this before writing or fixing `.tmdd/` YAML.

## Layout

```
.tmdd/
  system.yaml              # system metadata               (required)
  actors.yaml              # list of actors                (required)
  components.yaml          # list of components            (required)
  data_flows.yaml          # list of data flows            (required)
  features.yaml            # list of features              (required)
  threats/
    threats.yaml           # map threat_id -> threat       (required)
    mitigations.yaml       # map mitigation_id -> control  (required)
    threat_actors.yaml     # list of adversary profiles    (required)
  analysis/                # optional, written by this skill, ignored by tmdd
    stride_matrix.md       # coverage matrix + assumptions log
  out/                     # generated by tmdd; never hand-edit
```

Missing any required file => `tmdd lint` exits 2. YAML parse error => exit 2.
Validation errors => exit 1. OK (possibly with warnings) => exit 0.

## ID rules

Every ID (`actors[].id`, `components[].id`, `data_flows[].id`, threat keys, mitigation
keys, `threat_actors[].id`) must match `^[a-z][a-z0-9_]*$`. Convention for flows:
`df_<source>_to_<destination>` (shorten when long, keep source and destination readable).
Choose descriptive threat IDs that encode the location: `sqli_search_where_clause`,
`xss_stored_node_info`, `path_traversal_report_name`.

## system.yaml

```yaml
system:
  name: "Order Service"            # required
  description: "What it does"      # required
  version: "1.0"                   # required (threat model version, not app version)
```

## actors.yaml

Who legitimately interacts with the system (humans and external systems). Not adversaries.

```yaml
actors:
  - id: end_user                   # required
    description: "Authenticated shopper using the web storefront"   # required
```

## components.yaml

```yaml
components:
  - id: orders_api                 # required
    name: "Orders API"             # optional, shown in reports
    description: "FastAPI service exposing /orders/* (src/api/orders.py)"   # required
    type: api                      # frontend|api|service|database|queue|external|external_service|cache|other
    technology: "Python / FastAPI / SQLAlchemy"
    trust_boundary: public         # free text; use public|dmz|internal|external consistently
    source_paths:                  # globs relative to repo root, drive `tmdd review`
      - "src/api/orders.py"
      - "src/api/orders/**"
```

Glob syntax: `**` any characters including `/`; `**/` zero or more directory segments;
`*` any characters except `/`; `?` one character except `/`. No negation, no `{a,b}`.
Paths are compared with forward slashes, without a leading `./`.

`source_paths` guidance:
- One component per real architectural unit. If one directory holds several units
  (e.g. `src/commands/init.py`, `lint.py`, `review.py` are separate commands), split them
  into separate components with file-level globs rather than one `src/commands/**` hub.
- Include the unit's tests in its globs if you want test changes to surface its threats.
- Omit `source_paths` for third-party/external components and for generated output
  directories. Say why in a YAML comment. Such components are listed by `tmdd review`
  under "components with no source_paths".
- A changed file matching no component is reported as unmapped (`?`). Fix by extending a
  glob or adding a component, not by widening an existing glob to `src/**`.

## data_flows.yaml

```yaml
data_flows:
  - id: df_user_to_orders_api      # required
    source: end_user               # required, must exist in actors or components
    destination: orders_api        # required, must exist in actors or components
    data_description: "Order payload (items, address, payment token) as JSON"  # required
    protocol: HTTPS                # optional
    authentication: "session cookie + CSRF token"   # optional
    encryption: "TLS 1.2+"         # optional
    sensitivity: high              # optional; use low|normal|high|critical consistently
```

Flow guidance:
- One flow per real code path in a direction. A request/response pair is one flow unless
  the response carries materially different data (then two flows).
- Do not route everything through a single dispatcher flow. `tmdd review` marks a flow
  affected when *either* endpoint component matched a changed file, and then every feature
  declaring that flow is affected. Per-feature paths keep the review focused.
- `data_description` must name the actual data (credentials, PII fields, tokens, file
  bytes), not "API calls".

## threats/threats.yaml

A mapping, not a list.

```yaml
threats:
  sqli_search_where_clause:                      # key is the ID
    name: "SQL injection via string-built WHERE clause in search endpoint"   # required
    description: >-                              # required
      GET /api/search (src/routes/search.ts:38-47) concatenates the q parameter into
      the WHERE clause. Prisma's raw query helper is used without parameters, so a
      crafted q exfiltrates other tenants' rows. No WAF or input allowlist in front.
    severity: high                               # low|medium|high|critical (rubric in methodology.md)
    stride: T                                    # S|T|R|I|D|E
    cwe: CWE-89                                  # optional but include when known
    suggested_mitigations: [parameterized_search_query, search_input_allowlist]
    # each must exist in mitigations.yaml; required non-empty if any feature uses `default`
```

## threats/mitigations.yaml

A mapping. Two forms.

```yaml
mitigations:
  # simple form
  search_input_allowlist: "Validate q against ^[\\w\\s-]{1,64}$ in the search route handler before query construction"

  # rich form (preferred when the control exists or has a known home)
  parameterized_search_query:
    description: "Use Prisma parameterized query (Prisma.sql tagged template) for the search WHERE clause"
    references:
      - file: "src/routes/search.ts"     # must exist on disk relative to repo root
        lines: "38-47"                   # optional: "42" or "42-58"
```

`lint` checks that every `references[].file` exists (warning by default, error with
`--strict-refs`). A reference to a file that does not exist yet is a warning you should
not create: describe the planned control in prose and add the reference when the file
lands.

## threats/threat_actors.yaml

Adversaries, not users.

```yaml
threat_actors:
  - id: unauthenticated_internet_attacker
    description: "Anyone on the internet reaching the public API; no credentials, automated tooling, motivated by data theft or fraud"
```

## features.yaml

```yaml
features:
  - name: "Product Search"                   # required, unique (matched case-insensitively by `tmdd feature`)
    goal: "Let shoppers find products by free-text query"   # required
    input_data: [search query, session cookie]              # optional
    output_data: [product list]                             # optional
    data_flows: [df_user_to_orders_api, df_orders_api_to_db]   # must exist in data_flows.yaml
    threat_actors: [unauthenticated_internet_attacker]         # must exist in threat_actors.yaml
    threats:                                   # MUST be a mapping, never a list
      # scalar forms
      sqli_search_where_clause: default        # inherit suggested_mitigations from the catalog
      search_enum_rate_limit: [rate_limit_search]   # explicit mitigation list (override)
      verbose_search_errors: accepted          # risk accepted (needs a human reviewed_by)
      # object form (preferred): binds to flows and records lifecycle
      sqli_search_where_clause:
        mitigations: default                   # default | accepted | [ids]
        flows: [df_orders_api_to_db]           # subset of this feature's data_flows
        status: required                       # required | implemented | accepted
    last_updated: "2026-09-07"                 # set to today when you create/change it
    reviewed_at: "2000-01-01"                  # sentinel: forces a stale-review warning
    # reviewed_by: set only by a human after review. Never set it yourself.
```

(The duplicate `sqli_search_where_clause` key above only illustrates both forms; a real
file has each threat key once.)

Semantics of the object form:
- `flows` restricts where the threat lives. `tmdd review` surfaces the threat only when
  the diff touched one of those flows. Without `flows`, the threat is surfaced whenever any
  flow of the feature is touched. Every listed flow must be declared in the feature's
  `data_flows` and must exist.
- `status: implemented` means the control is shipped; a change on its flows shows up in
  review as "IMPLEMENTED - re-verify" with `[x]` boxes. `required` (default) is open work.
  `accepted` is equivalent to `mitigations: accepted`. `implemented` combined with
  `mitigations: accepted` is a lint error.
- Only set `implemented` when you verified the control in code and the mitigation entry
  carries a `references` pointing at it.

## Lint rules (what fails, what warns)

Errors (exit 1):

| Location | Rule |
|----------|------|
| any list file | top-level key must be a list; each item an object with a valid `id` |
| actors, components, threat_actors | `description` required |
| data_flows | `source`, `destination` required and must exist in actors or components |
| system.yaml | `name`, `description`, `version` required |
| threats.yaml | `threats` must be a mapping; each threat has `name` and `description`; `severity` in low/medium/high/critical; `stride` in S/T/R/I/D/E; every `suggested_mitigations` ID exists |
| mitigations.yaml | `mitigations` must be a mapping; value is a non-empty string or an object with string `description`; `references` is a list of objects with a string `file` |
| features.yaml | `name` and `goal` required; every `data_flows` and `threat_actors` ID exists; `threats` must be a mapping (a list fails unless `--no-mitigations`); every threat key exists in threats.yaml; every mitigation ID exists; `default` requires the threat to have non-empty `suggested_mitigations`; object form needs `mitigations`; `status` must be required/implemented/accepted; `implemented` + `accepted` conflict; `flows` must be non-empty, exist, and be declared by the feature; `reviewed_at` must be YYYY-MM-DD |
| mitigations.yaml with `--strict-refs` | a `references[].file` that does not exist |

Warnings (exit 0):

| Rule | Meaning |
|------|---------|
| feature has accepted threats but no `reviewed_by` | risk acceptance needs a human name |
| `last_updated` > `reviewed_at` | feature changed after last human review |
| `references[].file` not found (without `--strict-refs`) | drift or planned control |

Options: `tmdd lint [dir] [--strict-refs] [--repo-root DIR] [--no-mitigations]`.

## Review traversal (why modeling choices matter)

```
changed files --(components[].source_paths)--> components
              --(data_flows where source or destination is a matched component)--> flows
              --(features[].data_flows intersects)--> features
              --(features[].threats, filtered by each threat's `flows`)--> threats + mitigations
```

Consequences:
- `tmdd review` reads `git diff --name-only` only; **untracked new files are invisible**.
  Pass them explicitly: `tmdd review --files $(git ls-files --others --exclude-standard)`.
- Formats: `--format text|json|md`. Sources: working tree vs HEAD (default),
  `--base <ref>` (`<ref>...HEAD`), `--staged`, `--files ...`.
- Coverage gaps reported: changed files matching no component; components without
  `source_paths`.

## Other commands

```bash
tmdd init [dir] --template minimal|web-app|api -n "Name" -d "Description"   # scaffold; never over an existing model
tmdd feature "Name" -d "Description"   # not in features.yaml -> writes .tmdd/out/<name>.threatmodel.txt
tmdd feature "Name"                    # in features.yaml -> writes .tmdd/out/<name>.prompt.txt (secure implementation prompt)
tmdd compile [dir] [--feature "Name"]  # .tmdd/out/<system>.tm.yaml + <system|feature>.prompt.txt
tmdd-report [-p dir] [--format md|html] [-o outdir] [-n name]   # .tmdd/out/tm.md or tm.html
tmdd-diagram [-p dir] [-f "Feature"]   # .tmdd/out/diagram.html
```

Templates: `minimal` (skeleton), `web-app` (7 generic web threats), `api` (OWASP API
Top 10 style catalog). Template threats are placeholders: replace or specialize them with
code-grounded entries; delete template threats that do not apply rather than mapping them.

## Self-validation checklist

Before declaring any workflow done:

- [ ] Every component and flow cites real files; `source_paths` globs match existing files
      (`git ls-files | grep` to confirm) and are not directory-wide hubs.
- [ ] Every threat name/description names a component, endpoint, or file and describes the
      weakness in this code, with the input-to-sink trace, the reachability result, and
      severity assigned by the rubric.
- [ ] Every mitigation is concrete enough to implement; `references` point at existing
      files; `status: implemented` only where verified and the bypass analysis (alternate
      routes, ordering, encoding, fail-open) is recorded in the description.
- [ ] `features[].threats` is a mapping; object form used with `flows` where the threat is
      flow-specific; `flows` are declared by the feature.
- [ ] No `reviewed_by` written by you; `reviewed_at: "2000-01-01"` and `last_updated`
      today on features you touched.
- [ ] `accepted` only for user-confirmed decisions, with a comment naming who/why.
- [ ] Existing entries preserved; no duplicate IDs; template placeholders removed.
- [ ] `.tmdd/analysis/stride_matrix.md` written or updated, including the authorization
      matrix (or the one-line "single role" note), traces, sequence and state rows,
      dependency audit result, and reachability notes.
- [ ] `tmdd lint` exit 0; warnings reported to the user.
